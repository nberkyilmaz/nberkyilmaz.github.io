Selected work

Finding out why it's slow, and proving it

At Vretta I lead load testing for the platforms provinces run their exams on, from building the test environment to the report the client receives. Four pieces of that work, with the numbers behind them.

A sizing rule that matched production

How many API servers does an exam day need? From k6 and CloudWatch data I derived a simple rule: one server for every 1,000 students a day. In testing, a server reached the 30% CPU line at 98 requests a second, and 2025 production worked out to 99.

Production then ran 12,800 students a day on 15 servers, with peak-hour CPU under 20%.

Right-sizing a production database

The plan called for an 8xlarge RDS database. Benchmarking RDS and EC2 configurations under load, the 4xlarge held at 25.8% CPU in the stress test, while the API servers were forecast to reach 49 to 56%.

I recommended half the planned database and more API servers where they were needed, cutting planned infrastructure cost for two exam periods by an estimated 26 to 32%.

Test data with no real students in it

Realistic load tests need a copy of production with every trace of real students removed. I proved the existing data-masking script would have left 177,130 student IDs and birth dates in place, and wrote its replacement.

All 16 verification checks on the masked copy read zero.

Load tests that match production

A load test is only as good as the traffic it sends. I record real student flows, then check each API payload against production, because a 200 can be empty and still look like a pass. In one stress test, 8,000 students were online at once across the API, WebSocket, Redis and database layers.

Coverage of real traffic rose from 60% to 92% on a provincial program, and testing showed 16% of exam starts failing at 5× production's login rate.
